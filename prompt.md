# Steam Price Forecaster — Backend Implementation Prompt for Claude Code

You are the lead backend and machine-learning engineer for a production-minded application that forecasts Steam game discounts. Build the backend in this repository. Do not build a frontend. The frontend will be developed separately and must communicate with this backend through a documented, versioned HTTP API.

The product lets users search for Steam games, add them to a portfolio-style watchlist, inspect price history, receive probabilistic forecasts for the next sale and expected discount depth, get an explainable `BUY`, `WAIT`, or `NEUTRAL` recommendation, and receive notifications when important conditions are met.

Do not merely generate scaffolding or a design document. Inspect the existing repository first, preserve compatible existing work, then implement the system phase by phase. Keep the application runnable after every phase. If a credential is unavailable, implement the real integration behind an interface, add a development fake, document the required environment variable, and continue. Do not invent API responses or silently substitute mock production data.

## 1. Non-negotiable scope

Build only the backend, data pipeline, forecasting components, background jobs, tests, API documentation, and local/deployment configuration.

Do not build:

- Web pages, React components, CSS, or a mobile client.
- A generic deal marketplace that attempts to replace IsThereAnyDeal.
- A system that claims to know an exact future price or sale date with certainty.
- An LLM-based recommendation engine. Recommendations must come from explicit, testable rules and statistical forecasts.

The system must expose enough information for a separate frontend to render dashboards, charts, watchlists, forecast explanations, notification settings, and model-performance views.

## 2. Product behavior

A signed-in user must be able to:

1. Search for a game by title or resolve one from a Steam app ID.
2. View normalized game metadata, current Steam price, current discount, historical low, and timestamped Steam price history for a selected country/currency.
3. Add or remove a game from a watchlist.
4. Set preferences per watchlist entry:
   - Target price.
   - Minimum discount percentage.
   - Maximum number of days the user is willing to wait.
   - Notify only at a historical low.
   - Notify when the recommendation changes to `BUY`.
   - Enabled notification channels.
5. Receive forecasts containing:
   - Probability of any Steam discount within 7, 30, and 90 days.
   - Predicted discount tier conditional on a sale occurring.
   - Predicted price interval, not just a point estimate.
   - A likely sale window when the data supports one.
   - Confidence/data-quality score.
   - Short, structured explanation factors.
   - Model version and forecast creation time.
6. Receive an explicit `BUY`, `WAIT`, or `NEUTRAL` recommendation with a reason.
7. Receive deduplicated alerts through Web Push and/or email. SMS must be an optional adapter and must not be required for the MVP.
8. View historical forecasts and aggregate model-performance metrics through the API.

All monetary data must carry a currency code and region. Never infer an Indian Steam price by converting a US price to INR. Treat regional prices as separate observations. A global model may learn shared sale timing, but monetary predictions must use the requested region/currency.

## 4. High-level backend architecture

Implement the following logical components:

### HTTP API

Responsibilities:

- Authentication and authorization.
- Game search and lookup.
- Watchlist CRUD.
- Price history retrieval.
- Forecast and recommendation retrieval.
- Notification subscription and preference management.
- Forecast-performance endpoints.
- Internal health/readiness endpoints.

### PostgreSQL

The source of truth for users, normalized games, regional prices, sale events, watchlists, forecasts, recommendations, notification configuration, delivery attempts, model versions, and forecast outcomes.

### Redis

Use Redis for:

- Cache entries for external API reads.
- Celery broker/result needs.
- Distributed locks around ingestion/training jobs.
- Short-lived rate-limit counters if API rate limiting is implemented.

Do not treat Redis as durable application storage.

### Scheduled workers

Workers must:

- Refresh prices for watched games.
- Backfill history deliberately and incrementally.
- Normalize price changes into sale events.
- Recompute features and forecasts.
- evaluate forecasts after their horizons expire.
- evaluate alert rules and enqueue notifications.
- Retry transient failures with exponential backoff and jitter.

### Forecasting pipeline

The offline training pipeline creates versioned artifacts and evaluation reports. The online inference layer loads the active model once per process, validates feature compatibility, and returns forecasts. Inference must not train models.

### Notification pipeline

Use an outbox-style design:

1. A domain event or scheduled evaluation creates a notification event.
2. A transaction creates one or more notification outbox records with idempotency keys.
3. A worker sends through the configured provider.
4. Delivery state and provider response IDs are persisted.
5. Retries never create duplicate user alerts.

## 8. Forecasting approach

Steam prices are stepwise and promotion-driven, not continuously traded securities. Do not apply stock-price forecasting mechanically. Separate event timing from discount depth.

### Baseline first

Before advanced ML, implement a deterministic baseline using:

- Median interval between the game’s sale starts.
- Days since last sale.
- Typical and most recent discount tiers.
- Participation in recurring seasonal periods.
- Historical-low relationship.
- Publisher-level priors when game history is sparse.

The baseline must be used as a fallback when an ML artifact is unavailable or data quality is insufficient. Mark forecasts with their actual method.

### Model A: probability/time to next sale

Model the probability of a sale starting within 7, 30, and 90 days. Prefer either:

- Discrete-time survival analysis producing a hazard function, or
- A calibrated gradient-boosted classifier per horizon as the first production model.

Avoid reporting a precise date. Derive a likely window from the hazard/probability distribution only when it is sufficiently concentrated.

Candidate features:

- Days since the last sale ended and began.
- Median/mean/variance of prior sale intervals.
- Number of sale events in trailing 90/180/365 days.
- Previous discount depths and price tiers.
- Game age and release month.
- Calendar month, week, holiday/seasonal flags, and days until known Steam sale periods.
- Whether the title participated in analogous periods in prior years.
- Publisher/developer historical cadence.
- Genre/type and franchise information when legitimately available.
- Current price/discount and permanent-price-change indicators.
- Review score/count or popularity only when the permitted source and collection method are documented.
- Cross-store features only as optional enrichment, clearly separated from the Steam-specific target.

### Model B: discount tier conditional on sale

Predict discrete discount buckets, for example:

- `LT_20`
- `20_TO_29`
- `30_TO_39`
- `40_TO_49`
- `50_TO_59`
- `60_TO_74`
- `75_PLUS`

Persist the complete class probability distribution. Calculate price quantiles or intervals from class probabilities and regional regular price. Never output impossible negative prices or a currency-mismatched prediction.

### Cold-start behavior

For games with little or no history, use hierarchical fallbacks:

1. Game-specific history.
2. Publisher/developer cohort.
3. Similar age/genre/price cohort.
4. Global calibrated prior.

Return a lower confidence score and a reason such as `INSUFFICIENT_GAME_HISTORY`. Do not fabricate precision.

### Confidence and explanations

Confidence is not merely the maximum class probability. Derive it from:

- Amount and recency of history.
- Missing feature rate.
- Model calibration/performance for the applicable cohort.
- Predictive entropy or interval width.
- Out-of-distribution checks.

Return structured explanation factors, for example:

```json
[
  {"code": "RECENT_SALE_CADENCE", "direction": "WAIT", "importance": 0.31, "text": "Sales have historically started every 45–60 days."},
  {"code": "NEAR_HISTORICAL_LOW", "direction": "BUY", "importance": 0.24, "text": "The current price is within 5% of the recorded low."}
]
```

Explanations must be derived from rules or model explainability values and templates. Do not call an LLM to invent reasons.

## 9. Recommendation engine

Recommendations must be a separately versioned policy consuming current price, forecast, confidence, user maximum wait time, and historical statistics.

Start from:

```text
expected_future_price =
  P(sale in horizon) * E(price | sale) +
  (1 - P(sale in horizon)) * current_price

expected_savings = current_price - expected_future_price

wait_utility = expected_savings - waiting_cost
```

Make waiting cost explicit and configurable. Do not pretend it is objectively known. If no per-user urgency is available, use a documented conservative default based on maximum wait days.

Suggested policy behavior:

- `BUY` when the price is already near its regional historical low or expected savings from waiting are small relative to price, particularly when confidence is adequate.
- `WAIT` when calibrated sale probability and expected savings exceed configurable thresholds within the user’s horizon.
- `NEUTRAL` when evidence conflicts, confidence is low, or the expected benefit is marginal.

Store reason codes, thresholds, and ruleset version. Add unit tests for boundary behavior. All user-facing descriptions must use probabilistic language and label outputs as estimates, not guarantees or financial advice.

## 12. Model training and evaluation

Prevent temporal leakage. Use rolling/forward-chaining validation, never a random row split for time-dependent observations. A sample sequence is:

```text
train through March -> validate on April
train through April -> validate on May
train through May -> validate on June
```

Evaluate sale probability with:

- Brier score.
- Log loss.
- PR-AUC and ROC-AUC where meaningful.
- Precision/recall at the actual decision threshold.
- Calibration curves and expected calibration error.

Evaluate discount predictions with:

- Macro F1 and class-level metrics.
- Accuracy within one discount bucket.
- Mean absolute discount-percentage error.
- Price MAE/quantile loss.
- Prediction-interval coverage.

Evaluate recommendation policy with:

- Average realized savings relative to immediate purchase.
- Percentage of `WAIT` recommendations followed by a lower price inside the chosen horizon.
- Average time waited.
- Regret when `BUY` preceded a materially lower price.
- Results by confidence band and game-history cohort.

Compare every trained model to the deterministic baseline. Do not promote a candidate merely because one aggregate metric improved. Define promotion gates including calibration and cohort regressions. Persist metrics, cutoff dates, schemas, and artifact checksums.

Add a CLI or scripts for:

- History backfill.
- Feature dataset build.
- Baseline training/evaluation.
- ML training/evaluation.
- Candidate activation/rollback.
- Forecast generation for a game/region.
- Forecast-outcome evaluation.

### Phase 6 — ML training and inference

- Build leakage-safe datasets, boosted sale classifiers or survival model, discount-tier model, calibration, versioned artifacts, promotion gates, inference/fallback logic, and evaluation scripts.

Exit criteria: candidate metrics are compared with baseline, a model can be activated/rolled back, and production inference falls back safely if artifact loading fails.

### Phase 7 — Forecast accountability and hardening

- Implement outcome evaluation jobs, performance endpoints, calibration data, recommendation-regret reports, metrics, rate limits, security review, load-sensitive indexes, and complete operational documentation.

Exit criteria: historical forecasts remain immutable, matured forecasts are evaluated reproducibly, and tests/lint/type checks pass.

## 18. Definition of done

The backend is complete when:

- It runs locally with one documented setup flow.
- Migrations create a coherent constrained schema.
- A frontend can consume a stable `/api/v1` interface and generated OpenAPI document.
- IsThereAnyDeal access is cached, rate-limit-aware, server-only, and isolated behind a provider interface.
- Regional/currency correctness is enforced.
- Watchlists and alert preferences are user-authorized.
- Baseline forecasting works without ML artifacts.
- ML forecasts, when enabled, use versioned artifacts and leakage-safe evaluation.
- Forecasts are immutable and later evaluated against real outcomes.
- Recommendations are explainable, versioned, probabilistic, and tested.
- Web Push and email alerts work through an idempotent outbox; SMS is optional and disabled by default.
- No secret is committed or exposed in logs/API responses.
- Tests cover the critical workflow and failure modes.
- README documents setup, architecture, provider attribution/compliance, environment variables, commands, deployment, limitations, and model caveats.

When finished, provide a concise final report containing:

1. What was implemented in each phase.
2. Important architectural decisions and deviations.
3. Exact commands to run the API, worker, scheduler, migrations, tests, history backfill, and model training.
4. Required credentials and which features operate without them.
5. Test/lint/type-check results.
6. Remaining risks or manual launch steps, especially IsThereAnyDeal approval, email-domain verification, Web Push frontend service-worker work, and SMS compliance/cost.
